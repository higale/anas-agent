# 数据版本与升级迁移

当前应用自有持久化格式统一以显式 **v0** 为兼容原点。正常读取只接受当前格式，此前格式不提供自动升级或自动重置；手动抢救不受版本准入限制。应用发布版本与数据格式版本分别管理；LangGraph checkpoint、供应商协议、JSON Schema、通用 `.env` 和标准 `SKILL.md` 保留各自的原生格式。

## 当前数据版本

| 数据 | 版本位置 |
| --- | --- |
| 七份核心配置：settings、models、capabilities、subagents、mcp_servers、skills、tools | 顶层 `version: 0` |
| 随包项目默认值、模型及参数模板 | 顶层 `version: 0` |
| 项目存储、项目删除日志、输入历史、备份恢复事务日志 | 顶层 `version: 0` |
| 工具包 `TOOL.json`、语言包、头像裁剪参数 | 顶层 `version: 0` |
| 文件编辑的 definition.json、record.json | 顶层 `version: 0` |
| 模型列表缓存、语音列表缓存、外部临时文件登记 | 顶层 `version: 0` |
| HTTP 跟踪元数据、恢复保全清单 | 顶层 `version: 0`；原始请求和响应内容不改写 |
| catalog、会话 SQLite 数据库 | `PRAGMA user_version = 0`；数据库内的应用记录由所属数据库版本管理 |

SQLite 的默认版本也是 0，因此只有无应用表的空库才初始化；已有库必须通过版本和表结构检查，不能把未知或损坏的库当作空库重建。原始附件、脚本、图片、日志文本及用户文件不增加应用版本字段。

配置在读取时先检查版本，再解析内容；写入时明确保存当前格式版本。缓存的缺失或失效沿用缓存自身的重新获取流程。当前有效数据在移除具体升级模块后，仍须能够正常启动、读取、保存和执行。

## 手动数据修复

启动恢复页的“修复”是最后的数据抢救入口。所有出错文件均保留修复操作，不因版本、缺少升级路径或预检未找到可修复字段而隐藏入口。版本缺失或不匹配均按字段错误修正；正常业务读取仍不容忍错误格式。

七份核心配置、项目元数据、输入历史和头像资产均纳入恢复检查，尽力保留有效设置、身份和引用，修正可确定的错误字段，结果使用当前解析器校验。缺失的核心配置可用当前默认值重建；不能凭空编造项目身份或重置会话。修复前保全原始数据；无法解析的文件也会保全并报告具体问题，不以重置冒充修复。

输入历史和头像资产在主界面打开前检查，失败进入统一恢复页。输入历史逐条抢救可识别记录，保留其顺序及元数据，不额外裁剪或去重；坏条目保留在原文副本中，结果报告部分修复。非空历史若没有可识别条目，保留原文件并报告问题，不替换为空历史。

头像检查覆盖原图、裁剪图、显示图及平台所需衍生图。独立的 [`recoveryAvatar.ts`](../src/main/recoveryAvatar.ts) 从仍可读取的原图或裁剪图抢救，必要时使用保留下来的显示图；先保全原始资产，再通过既有头像资产事务重建缺失或损坏的内容。没有可恢复图像时报告问题，不静默改用默认头像；可选头像资产尚不存在时交由正常初始化处理。

项目修复在独立暂存副本中检查 catalog 与所有会话库，包含未 checkpoint 的 WAL。每库分别按当前结构、完整性、归属和附件引用校验；校验通过的副本修正 `user_version`，失败的库保留原始文件族并报告问题，不阻断其他可抢救数据。项目元数据及 SQLite 目录通过现有恢复日志一起替换，失败回滚，中断后可继续回滚；保全失败或源数据在检查后变化则不覆盖源数据。整个过程不运行 Agent、不重放工具，也不改变 LangGraph 原生版本。

会话库修复同时检查已归档的文件修改记录：补齐或修正应用格式版本，重算定义校验值及同库撤销关系中的引用，保留原消息、文件内容快照、操作身份和执行状态。仅修正元数据且操作定义不变时，原样保留目标已不在本库的历史引用，不因关联轮次已删除而阻断修复。原始校验值或内容损坏时保留原库并报告问题；仍有外部恢复材料，或定义需要改写却缺少关联记录时，须连同这些材料处理，不能只改归档而使恢复证据不一致。

没有对应删除日志的 `projects.json.delete-stage` 只表示未完成的暂存写入，不阻断项目修复；原文件及保全副本均保留，不把暂存内容当作已提交的删除事务。

## 独立迁移框架

迁移集中在 [`src/main/migrations/`](../src/main/migrations/index.ts)。业务模块只处理当前格式，不引用具体升级模块，也不在读取时转换旧数据。入口在构建时自动发现 `upgrades/*.ts`；**当前没有升级模块**，入口执行空流程。

- 启动：回滚中断的备份恢复事务后、首次业务读取前，调用 `migrateDataDirectory`。迁移失败进入启动恢复界面。
- 备份恢复：解压并检查必需文件后，在暂存目录调用相同入口，再校验当前数据；头像参数存在时只读检查版本和结构，不生成图像。校验成功后才切换数据目录，避免导入错误头像参数后直到重启才失败。
- 调用方保证独占：启动使用应用数据锁，恢复使用自己的暂存目录。业务运行期间不对正式目录执行迁移。
- 缺失文件不由迁移框架创建。新安装由初始化生成默认值，缺少必需文件的备份由恢复流程拒绝。

[`framework.ts`](../src/main/migrations/framework.ts) 执行显式的 `from → to` JSON 升级链。当前版本立即跳过，旧版本在内存中转换并校验目标结构；缺失版本、未知新版本或缺少升级路径均拒绝。所有注册文件预检成功后，才逐文件备份原始内容到 `.v<源版本>.bak`，再原子替换。已有备份必须与待升级源文件一致，不会被覆盖。

每个文件独立原子提交，可在失败后重试：已完成文件跳过，未完成文件继续。整个流程成功前不启动正常业务。这不是跨文件事务；涉及跨文件引用或 SQLite、框架序列化格式变化时，必须在独立迁移目录增加具备暂存、日志及回滚能力的事务迁移单元。

## 后续新增迁移

1. 某种格式从 v0 变更时，只递增该格式版本，并在 `upgrades/` 添加独立步骤；保留支持跳版本升级的完整路径。
2. 升级函数仅转换数据，不执行工具或重放外部操作；当前结构校验可以复用共享纯校验器，不依赖业务 Store 或运行时。
3. 同步默认文件、持久化类型、保存和读取路径；保留 ID、选择和引用关系。
4. 用已发布基线样本验证升级、重复执行、未知版本拒绝、备份及写入失败重试。删除受支持的升级路径须经用户明确同意。

运行 `npm run test:e2e -- --current-data-only` 验收无升级模块时的 v0 初始化、读写、重复启动，以及配置缺版本、tools v1、projects v4、SQLite v1、输入历史和头像配置的手动修复、原文保全与重启。部分抢救、WAL 和失败回滚由行为测试覆盖；通用自动升级链由迁移框架单元测试覆盖。
