### 第二阶段：偏好记忆（待单独安排）

目标：以简短 Markdown 保存全局／项目偏好，固定带入模型上下文；前台提交记忆要求，后台延后合批整理，允许最新偏好延迟生效。

已确定边界：

- 全局偏好放在 `db/MEMORY.md`，项目偏好放在 `db/projects/<项目ID>/MEMORY.md`。Markdown 是唯一权威记忆正文，不在数据库重复维护正文，也不另设摘要文件。
- 每次组装模型请求时，按记忆能力设置固定带入已整理的全局及当前项目偏好，并纳入上下文预算与预览。文件缺失或为空时不注入；读取失败不能冒充空记忆。
- 仅记录明确、可复用的偏好，不把一次任务要求提升为永久规则，不保存与代码版本绑定的特殊结论。此类项目规则或经验可放在实际工作目录，由用户决定是否提交 Git。
- 前台模型调用专用工具，提交新增、纠正或删除偏好的自然语言要求及作用域，不生成完整记忆正文或 patch。程序绑定项目、来源会话和相关用户表达，持久化请求后立即返回“已记录／待整理”，不能宣称已经整理生效。
- 后台只处理明确提交的记忆要求，不自动扫描全部历史会话推断记忆。整理模型读取现有正文、本批请求及必要来源，合并相近内容、消除重复、应用明确纠正与删除，保留条件和作用域；不能凭时间较晚就覆盖不明确的冲突，不能把项目偏好擅自提升为全局偏好。
- 设置中增加可选的后台记忆模型选择；默认不选择，使用触发整理时正在使用的模型。触发时确定本批整理模型，避免随后切换会话或模型影响已调度任务。
- 切换会话、继续回复均不等待整理。新会话直接使用已完成记忆，不额外注入待整理要求；通过 UI 告知最新偏好可能尚未生效。
- 用户无需理解整理机制，不提供或依赖“立即整理／现在生效”之类的专门用户指令作为流程条件。

触发与调度：

- 有待处理请求时，切换会话经短暂防抖触发；快速来回切换不能重复创建任务。
- 上下文压缩开始前确认记忆请求已持久化，同时调度记忆整理。压缩和整理使用各自输入快照并行执行，互不等待；压缩完成后继续对话，整理完成后独立更新记忆与 UI。任一任务失败不导致另一任务失败。
- 待处理请求达到数量或文本长度门槛、用户空闲、最早待处理请求等待过久时，均可触发合批整理。空队列不调用模型；最长等待以未处理请求的年龄计算，不能因不断收到新请求而无限延后。
- 重启后恢复待处理请求和中断任务；退出不要求等待整理完成。
- 多种条件统一进入一个调度入口。同一份记忆串行整理，跨会话请求合并排队；不同作用域可以独立调度，并限制后台总体并发。具体阈值在实现时确定，不把此前讨论的示例数值当作已定默认值。
- 每次固定请求批次及正文版本，处理期间的新请求留到下一批。保存前核对正文未被其他入口修改，冲突则重新读取后整理；校验后原子保存，成功后才确认该批请求完成。覆盖保存与任务确认之间的中断须可恢复，不能丢请求或重复应用已完成变更。
- 失败保留请求并退避重试；不把用户请求记录为已完成，不生成空正文覆盖有效记忆。

UI 状态：

| 状态 | 标记 |
| --- | --- |
| 有请求等待处理 | 记忆待整理 |
| 后台正在整理 | 正在整理记忆 |
| 整理失败、保留重试 | 记忆整理失败，将重试 |
| 全部请求已完成 | 清除标记 |

待处理／运行中的提示说明：“最新偏好尚未整理完成，可能还未在其他对话中生效。”状态作用域必须清楚；本批完成但仍有新请求时继续显示待整理，不能提前清除标记。
